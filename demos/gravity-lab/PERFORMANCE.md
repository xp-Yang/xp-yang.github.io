## 当前目标与测量边界

目标是提高 1000 球的实际物理推进率，同时保留牛顿引力、连续硬球碰撞和恢复系数 e。20× 是用户设置的目标推进率，不是当前实现的性能保证。GPU 全对求和和接触预测仍为 `O(N²)`；冷球云聚集后的密集事件、接触短步、GPU 调度与读回可能成为瓶颈。需分别记录核心推进、标量读回、完整快照和诊断成本，不能以 GPU 可用或单次求力速度推算作品实际倍速。

## 当前实现：2026-10-13 GPU 常驻积分与 CCD

`src/physics/webgpu-simulation.js` 管理常驻 GPU 状态，WGSL 管线执行全对牛顿求和、Kick–Drift–Kick 积分与连续事件碰撞；CPU Float64 八叉树和直接求和仍可选。GPU 求力使用 64 球共享内存分块与补偿累加，不增加引力软化。GPU 不再在每次求力后把加速度回读到 CPU 积分。

位置、速度、加速度以及试算与已提交状态常驻 GPU。位置相对固定原点保存，另有 f32 `positionError` 和已提交余量；漂移保留 FMA 乘积误差，避免接触前的小位移被大坐标舍入吞掉。引力与 CCD 的距离计算扣除位置余量，CPU 完整快照按“位置高位 − 余量 + 原点”重建。运算仍全部为 f32，不等价于 Float64，也不增加额外碰撞阻尼。

每个 Drift 首先并行预测所有球对的绝对接触时间，经归约选择最早事件；同刻事件按球对编号确定顺序，单个事件顺序施加等质量法向冲量。事件后仅更新与参与两球有关的 `2N−3` 个预测，其余球对保持既有绝对时刻。接触短步、失败预算和恢复系数 e 的耗散规则保留，密集接触不能通过跳过事件来追赶目标倍速。

GPU 状态机使用间接调度参数决定每一阶段是否执行，顺序 dispatch 提供阶段之间的同步，不使用跨工作组自旋等待，也不并发处理互相关联的接触冲量。每批最多 16 个阶段槽位，每槽可处理 2 个事件；槽数按剩余目标与实际已提交推进量估计，减少短目标的空调度。尚未结束的试算可跨批次继续。只有完整 KDK 子步通过校验才一起提交球体状态、时间、事件数与耗散；重试从已提交备份恢复，未完成或失败的试算不计入模拟时间，不作为画面发布。

碰撞预预测先做保守扫掠轴剔除，球对索引表只在上传时生成。首次大步 probe 使用时间舍入窗口，并对不确定根补做局部尺度的步尾接触检查，避免用世界坐标接触容差除以速度把下一步的碰撞提前拉进当前步。实际短步事件仍保留接触容差与失败回滚。TOI 和冲量都用相同的 `diameter ± tolerance` 区间判断接触，避免两种数学等价表达式在 f32 边界上不一致而永久拒绝零时刻事件。

每个批次仅读回轻量标量元数据；Worker 每片目标软预算 8 ms，GPU 批次或诊断可能超过预算。约 30 Hz 再完整读取已提交位置、速度、加速度和匹配元数据，保存为 CPU checkpoint，并通过 transferable 快照供主线程 Three.js WebGL 渲染。约每秒在完整状态上进行 CPU 精确势能与抽样求力误差诊断。渲染没有直接共享 GPU 物理缓冲；当前读回使用复用单缓冲和串行等待，尚未实现读回双缓冲重叠。

网页初态的空间哈希拒绝重叠采样仍在 CPU。导入状态的初始接触准备、初始速度归一化和诊断基线也由 CPU 准备；首次 GPU 上传完成初始求力与完整快照后建立基线。实时参数在完整已提交状态边界应用。已有 GPU 状态的配置更新恢复已提交状态、写入参数并重算引力，保留球体和球对缓冲；e 改变保留基线与累计耗散，密度改变按原规则重建基线与耗散累计。

Worker 的重置、配置、播放、计算与快照进入同一个串行队列。启动时 WebGPU 不可用、设备创建或首次上传失败会自动选择 CPU；运行期 GPU 错误则恢复最近完整 CPU checkpoint、释放 GPU 并暂停，用户点击播放后才用 CPU 继续。最近完整快照之后未回读的 GPU 进度可能丢弃，不声称同一步无损恢复；暂停确认避免此前排队的播放消息自动续算。显式选择 CPU 前先同步完整状态并重算 CPU 加速度。

当时的手动入口 `/benchmark-resident.html`（现已移除）比较均匀球云、低紧密度均匀球壳、对称球壳与最稀均匀球壳四个场景，以及 CPU 直接求和、旧 GPU 求力＋CPU CCD、GPU 常驻仅最终完整快照、GPU 常驻加约 30 Hz 快照四种模式。每个案例以独立状态热身，再从新初态计时，初始化、最终完整快照与诊断单列；周期快照模式把读回成本计入推进墙钟时间。入口只手动运行，不含断言或测试，也不进入作品生产构建。

当时的 CPU 内核优化约快 2 倍；GPU 求力＋CPU 积分方案在本机浏览器前 1 模拟秒中，完整积分又比当时 CPU 八叉树快约 1.6–2.1 倍，尚未达到“轻松 20×”。这些结果只覆盖所列历史实现和推进区间，不能推算当前常驻 GPU 版本、长期坍缩阶段、作品渲染中的实际倍速或所有设备的稳定性能。

## 历史：CPU 瓶颈和优化方案

1. **引力树内存与遍历。** 原实现每次求力创建节点对象、分桶数组和遍历栈。当时改为由 Simulation 持有可扩容 TypedArray 工作区，稳定分区建树，用 open/next 指针遍历，按叶桶顺序缓存连续坐标。保持桶大小 8、深度上限 40、几何包含判定、开角 θ 和原来的节点/叶内求和顺序。直接求和接口仍可用。
2. **碰撞宽相。** 用复用 TypedArray 开放寻址哈希替代每次创建 Map 和单元对象。单元宽度仍为直径加漂移期间两倍最大行程，27 个邻接单元保守覆盖能相遇的球对。拒绝较大含接触试步时只预测第一个事件，不构建后续事件堆。
3. **碰撞事件。** 每次漂移用索引堆缓存绝对事件时间。碰撞后只更新两参与球与其他球的 2N−3 对，因为未参与球的直线轨迹没有改变。参与球全量检查新伙伴，覆盖反弹后的新接触；相近事件仍按球 ID 排序。1000 球约 8 MiB 的球对索引在首次实际事件时分配，之后复用。漂移结束后的队列不跨积分步复用。
4. **接触前逼近。** 被拒绝的试步改为瞄准预测接触时刻，取代原来的 80% 几何逼近；保留半步缩减上限、接触短步下限和每次重新 CCD。由于半 kick 随 dt 改变，旧预测只指导下一次尝试，不能直接作为接受依据。实际含冲量的步仍受原 contactDt 约束。非接触步分割会变化，因此并非逐位相同的积分轨迹。
5. **后台调度。** Worker 自主连续计算，每片软预算 8 ms；MessageChannel 在片间让出事件循环，避免连续 setTimeout 的嵌套计时器间隔。快照约 30 Hz，主线程相机与渲染独立运行。目标按实际经过时间累积，最多保留 100 ms 墙钟对应的目标进度；不跳过物理时间或漏算碰撞。暂停、隐藏、显卡中断与重置使旧调度失效，恢复重新计时。单步仅在暂停时推进；播放确认后重新统计倍速，避免混入旧速度进度。
6. **积分辅助开销。** 最大速度和加速度改为平方范数比较后各开平方一次；接触精度常数每批计算一次。极大导入状态回退 hypot；不可推进时间步安全停止，避免后台死循环。

碰撞失败仍回滚整个原子步。e、累计耗散与能量基线的定义不变，初始条件仍点击“应用”后生效。8 ms 是目标预算，单个完整物理步或诊断可以超过预算。

## 历史：GPU 求力＋CPU 积分实现

2026-10-12 的方案新增 `src/physics/webgpu-forces.js`，只把求力放到 GPU，保留为历史计时对照：64 球共享内存分块，全对牛顿求和，跳过自身，不使用引力软化。全对求和仍是 O(N²)，GPU 并行执行；f32 坐标在上传前减去包围盒中心，着色器使用补偿累加减小求和误差。管线、上传数组、存储缓冲和单个读回缓冲在多次求力中复用。[Chrome 官方计算着色器说明](https://developer.chrome.com/docs/web-platform/webgpu/from-webgl-to-webgpu)、[NVIDIA N-body 分块求和资料](https://developer.nvidia.com/gpugems/gpugems3/part-v-physics-simulation/chapter-31-fast-n-body-simulation-cuda)。

`Simulation.advance` 与 `advanceAsync` 共用同一个 generator，保留原 KDK、连续漂移、接触短步和回滚规则。位置、速度、碰撞与积分为 CPU Float64；GPU 求力和输出为 f32。每个成功漂移等待求力后，才提交末端 kick、时间、事件和 e 耗散；失败求力在同一位置回退 CPU，两个后端都失败则恢复原子步。初始化求力完成后才建立基线。GPU 求力 RMS 始终采样对比 CPU Float64 直接求和，不能沿用“直接模式误差恒为零”。

当时 Worker 的 reset、configure、playback、advance 与自主 pump 进入同一个串行队列；GPU 等待期间不会用新模拟替换旧数组。GPU 求力默认启用，CPU 八叉树和直接求和仍可选择，开角仅在树模式启用。“误差”页显示实际后端，回退原因作为悬停提示。无硬件适配器、不支持 API、编译/设备错误、5 秒等待超时或 f32 数值范围问题均回退 CPU；软件 GPU 适配器不作为加速后端。显式切换回 WebGPU 可重新尝试初始化。设备丢失与 dispose 拒绝在途等待，成功完成的等待会移除订阅，避免长期积累。此处为历史方案的错误处理；当前常驻方案运行期错误按上文恢复 checkpoint 并暂停。

该历史方案每个引力更新都要回读 CPU，不能保证所有场景更快。2026-10-13 已实现位置与速度常驻 GPU、批量积分、GPU 接触预测与最早事件归约、按事件顺序处理接触及 e 耗散。画面仍通过完整读回快照交给 WebGL 渲染，没有直接共享 GPU 状态；20× 仍不能由这些架构变化推断。
